## Anthropic

### [UPDATE] Claude Code: /fork → background sessions, /resume picker, WebSearch rate limit

**Background:** July 16's update covered v2.1.208 (screen reader mode, vimInsertModeRemaps, Admin Console Usage/Value tabs). These changes landed in the same release cycle.

**New:**
- `/fork` now spins up a full background session — its own row in `claude agents`, independent lifecycle — rather than running an in-session subagent alongside the current conversation. The old inline subagent behavior is now `/subtask`.
- `/resume` in the agent view opens a picker of past sessions, including deleted ones, and resumes them as background sessions instead of replacing the current conversation.
- Background sessions created with `/fork` no longer lose live-parent protection after a state write failure (was silently dropping the protection flag).
- Reduced memory footprint when resuming large conversations that had background agents or forks.
- WebSearch rate limit added: 200 calls per session by default, tunable with `CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION`. Prevents runaway search loops in agentic flows.
- Auto-retry on transient server-side rate-limit errors now applies to subscribers.

Sources: [Claude Code Changelog](https://code.claude.com/docs/en/changelog), [Gradually.ai Claude Code changelog](https://www.gradually.ai/en/changelogs/claude-code/), [Releasebot Anthropic](https://releasebot.io/updates/anthropic/claude-code)

**Why it matters:** The /fork-to-background change is a semantic shift: long-running parallel work is now a first-class background citizen, not a fragile in-session branch. The WebSearch cap is directly relevant when building Routines that search the web — a 200-call hard cap with a tunable env var is exactly the kind of guardrail you want to be aware of before hitting it in production.

## Tools & Frameworks

### [NEW] Grok Build security incident: entire repos uploaded to xAI cloud, open-source response leaves exfiltration code intact

Wire-level analysis published around July 12 proved that xAI's Grok Build CLI was packaging tracked Git repos in full — complete history, committed secrets, SSH keys, password manager databases — and uploading them to a Google Cloud Storage bucket operated by SpaceXAI. The upload-to-actual-need ratio in one documented case was 5.1 GB sent vs. 192 KB required (~27,800×). xAI had explicitly marketed Grok Build with the claim "nothing from your codebase transmitted to xAI servers during a session," and the in-app privacy toggle had no effect on the uploads.

Musk posted a commitment to delete all previously uploaded user data. The Register, The Next Web, and TechTimes all independently confirmed the bucket destination and the privacy-toggle bypass. On July 16, xAI open-sourced Grok Build under Apache 2.0 (844,530 lines of Rust). Post-publication analysis found the exfiltration code remained present in the released source.

Sources: [The Register](https://www.theregister.com/ai-and-ml/2026/07/14/musk-promises-purge-after-grok-build-caught-sending-entire-repos-to-the-cloud/5271123), [The Next Web](https://thenextweb.com/news/grok-build-uploaded-entire-git-repositories-secrets), [TechTimes — incident](https://www.techtimes.com/articles/320420/20260714/grok-build-shipped-entire-codebases-xai-cloud-privacy-toggle-did-nothing.htm), [TechTimes — open-source](https://www.techtimes.com/articles/320671/20260716/grok-build-open-sourced-after-covert-upload-code-exfiltrate-repos-stays.htm), [Axios](https://www.axios.com/2026/07/14/spacexai-grok-customer-data)

**Why it matters:** A coding tool that silently exfiltrates full repo contents — including credential files in home directories opened during the session — is a meaningful category of risk for anyone running AI dev tooling. The open-source release doesn't neutralize the concern while the upload code is still present.
