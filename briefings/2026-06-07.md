## Anthropic

### [NEW] Managed Agents: self-hosted sandboxes in public beta, private MCP tunnels in research preview

Announced at Code with Claude London (May 19) but not previously captured here. The headline: with self-hosted sandboxes, tool execution moves into infrastructure you control while Anthropic still runs the orchestration loop (context management, error recovery, retry logic). Supported sandbox providers are Cloudflare, Daytona, Modal, and Vercel, or you can bring your own host. MCP tunnels — letting Managed Agents reach private MCP servers inside your perimeter without opening inbound ports — are also shipping, in research preview.

The architectural split matters: code the agent writes and runs, files it reads, and all network egress stay on your host with your existing audit logging and network policy in place. Anthropic's side only sees tool invocations and results, not raw file contents.

Sources: [Anthropic blog](https://claude.com/blog/claude-managed-agents-updates), [platform docs](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes)

**Why it matters:** If you're building agents in v1-routines that touch sensitive repo content or internal APIs, self-hosted sandboxes are the production path — you keep data inside the perimeter without rebuilding the agent loop.

## Tools & Frameworks

### [UPDATE] Claude Code v2.1.166/167: fallbackModel, glob deny rules, MCP timeout fix

**Background:** v2.1.164–165 (June 5) were mostly CI/CLI auth fixes and bazel tmpdir edge cases.

**New in v2.1.166 (June 6):**
- `fallbackModel` setting: configure up to three backup models (array) tried in sequence when the primary model is overloaded or unavailable. Reduces the "rate limit stalls your agent" problem for long-running workflows.
- Glob pattern support in deny rule `tool-name` position: `"*"` in a deny rule now blocks all tools in scope; `allow` rules correctly reject non-MCP globs and warn at startup if an unknown tool name appears in a deny rule.
- MCP per-server timeout bug fix: any configured value below 1000 ms was being silently floored to a 1-second watchdog that aborted every tool call immediately. Sub-1000 ms values are now ignored (falling back to `MCP_TOOL_TIMEOUT` or default) and `claude mcp get` annotates the affected servers.
- OTEL: `OTEL_RESOURCE_ATTRIBUTES` values are now included as labels on metric datapoints — slice usage by team, repo, or environment in your observability pipeline.

v2.1.167 (June 6) was a bug-fix-and-reliability follow-on with no new user-facing changes.

Sources: [Claude Code changelog](https://code.claude.com/docs/en/changelog), [Releasebot](https://releasebot.io/updates/anthropic/claude-code)

**Why it matters:** The MCP timeout bug is a silent foot-gun — if your MCP server response target was set under 1s in config, every tool call was failing at exactly 1s regardless. Check your per-server timeout settings.

### [NEW] ChatGPT Memory Dreaming V3 extends to Free users

OpenAI's background memory synthesis engine reached Free-tier ChatGPT users on June 4–5 (Plus/Pro had it earlier). Instead of a manually curated memory list, "dreaming" reads across years of past conversations and auto-revises what the system knows about you — time-aware, so "going to Singapore in July" becomes "went to Singapore" after the trip passes.

User-facing additions: a readable memory summary page, controls to add/update remembered details, and per-topic raise settings. Plus and Pro users also get 2x memory capacity. The Free rollout was gated on achieving a roughly 5x reduction in compute cost of serving the dreaming process at scale.

## Research & Technical

### [NEW] BAGEN: frontier agents are not budget-aware (arXiv 2606.00198)

Northwestern (O2 Lab) paper benchmarks five frontier agent systems across four environments on a specific question: can the agent accurately predict how much budget (tokens/actions) it will still need mid-execution, and does it stop early when a task is unlikely to succeed?

Key findings:
- Task performance and budget awareness are weakly correlated (r = 0.35) — strong agents are not necessarily budget-aware agents.
- All tested frontier agents are systematically over-optimistic: they continue spending on failing trajectories rather than surfacing early-exit signals.
- Early stopping on detected-failing trajectories saves 28–64% tokens.
- SFT + RL training on budget-aware signals improves calibration but interval coverage caps at 47% — precise interval estimation remains unsolved.

The paper formalizes budget awareness as "progressive interval estimation": mid-run, can the agent bound how much budget remains required? It tests both internal budgets (from computation) and external budgets (from agent actions).

Source: [arXiv 2606.00198](https://arxiv.org/abs/2606.00198)

**Why it matters:** If you're running deep agent workflows in v1-routines and burning through Max plan quota on tasks that are already off the rails, this gives you a framework and vocabulary for the problem. The "early stop" heuristics are implementable today even without training.
