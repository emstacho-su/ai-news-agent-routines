# Follow-up: TrustFall: one-keypress RCE in Claude Code, Gemini CLI, Cu

**Q:** What's the safest way to evaluate a new third-party MCP server before adding it to my Claude Code config? Specifically interested in any sandboxing or containerization patterns that would actually mitigate TrustFall-style attacks.

**A:**

The cleanest defense-in-depth stack right now is: **static review before install → Claude Code native sandbox runtime for isolation → Docker microVM for CI**. Here's the concrete breakdown.

---

## Pre-install review (zero-trust gate)

Before adding anything to `.claude/mcp.json` or `settings.json`:

1. **Inspect tool descriptor metadata.** Read the server's source — specifically every `description` field on every tool. Researchers successfully poisoned 9 of 11 tested MCP marketplaces with injected instructions hidden in tool descriptions. The attack surface is the metadata, not just the binary. ([OX Security supply chain advisory](https://www.ox.security/blog/mcp-supply-chain-advisory-rce-vulnerabilities-across-the-ai-ecosystem/))

2. **Verify against the official metaregistry.** `registry.modelcontextprotocol.io` is the Anthropic-backed canonical source — machine-readable JSON, packages live on npm/PyPI/Docker Hub. Being listed there is a necessary-but-not-sufficient signal. Do not install from Smithery, MCPMarket, Glama, etc. alone — verify the source repo on GitHub directly.

3. **Check the OX/TrustFall threat model.** 66% of scanned public MCP servers had at least one security finding in recent audits. Treat everything outside the Anthropic reference set (`modelcontextprotocol/servers` — Memory and Sequential Thinking) as untrusted by default.

---

## Runtime isolation: Claude Code native sandbox (most direct TrustFall mitigation)

Anthropic shipped a native sandbox runtime (beta/research preview) that runs arbitrary processes — including MCP servers — inside filesystem + network namespace isolation on Linux. This is the most targeted fix for TrustFall-style spawn-as-OS-process attacks:

- Define per-MCP-server allowed directories and network hosts in your sandbox config
- `enableWeakerNestedSandbox` mode supports running inside Docker without privileged namespaces
- The sandbox scopes what the MCP server process can reach, even if the trust dialog is accepted

Docs: [Claude Code Sandboxing](https://code.claude.com/docs/en/sandboxing) | [Anthropic Engineering post](https://www.anthropic.com/engineering/claude-code-sandboxing)

**Critical gap this closes:** TrustFall's root issue is that `enableAllProjectMcpServers` / `enabledMcpjsonServers` bypass produces an unsandboxed OS process with your full privileges. The native sandbox runtime constrains that process even after spawn. It does not prevent the server from being invoked — it limits what the server can do once running.

---

## CI headless path: Docker microVM (zero-interaction exposure)

TrustFall is zero-interaction in `claude-code-action` pipelines — the trust dialog is skipped entirely. For CI:

- **Docker Sandboxes** (launched January 2026) run Claude Code + its MCP servers inside a dedicated microVM (separate kernel, private Docker daemon). Package installs, file writes, and spawned processes from within the microVM cannot touch the host. This is the most turnkey option for headless agentic runs. ([Docker Sandboxes blog](https://www.docker.com/blog/docker-sandboxes-run-claude-code-and-other-coding-agents-unsupervised-but-safely/)) | ([Claude Code + Docker](https://www.docker.com/blog/run-claude-code-with-docker/))
- Audit your `claude-code-action` pipeline inputs: any repo you clone gets its `.mcp.json` auto-trusted in headless mode. Add a pre-run step that fails the pipeline if `.mcp.json` or `.claude/settings.json` contains `enableAllProjectMcpServers: true` or `enabledMcpjsonServers`.

---

## Linux userspace sandboxing (firejail / bubblewrap / nsjail)

These tools can wrap stdio MCP server processes — but there are no published MCP-specific profiles as of this writing. It's viable but currently DIY. The Claude Code native sandbox is a more ergonomic path to the same isolation boundary.

---

## What doesn't exist yet

- Static analysis tools for MCP server capability auditing (no public tooling)
- Marketplace-level vetting scores or automated trust signals

Both are gaps. If you want the highest assurance today: use only servers you've read in full, run them under the native sandbox runtime, and wrap your CI in a Docker microVM.
